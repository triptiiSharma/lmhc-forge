## What this is (terminology, frozen per the approved plan)

`nvdisasm` is a second, independent **disassembly and parsing path** over
the same NVIDIA cubins already compiled for the core matrix. It is **not**
independent semantic ground truth — both `nvdisasm` and `cuobjdump`
interpret the same binary encoding produced by the same `ptxas` backend.
What agreement between the two demonstrates is that the primary
(`cuobjdump`/`sass_parser.py`) structural-signature checker isn't an
idiosyncratic artifact of one tool's text formatting or one parser's
implementation choices. This document reports **category agreement** and
**feature agreement**, never "accuracy."

## Implementation

- `scripts/nvdisasm_parser.py` — independent parser consuming
  `nvdisasm -c -json` output directly (structured `opcode`/`operands`/
  `predicate`/`other-attributes.control-flow` fields). Confirmed, before
  writing this parser, that both CUDA 12.8 (V12.8.90) and CUDA 13.3
  (V13.3.29) emit the same top-level JSON shape (`[metadata, [function,
  ...]]`) with the same required function/instruction keys — 13.3's
  metadata dict carries 2 extra keys not present in 12.8's, which doesn't
  affect instruction parsing. Schema is validated explicitly
  (`validate_schema()`); a document that doesn't match fails with a
  recorded reason rather than a guess.
  - Register-mediated (indirect) zero-store tracking is re-implemented
    independently against the structured `operands` field (not the
    text-regex approach `sass_parser.py` uses) — same conservative
    last-write-wins principle, applied to a completely different data
    representation.
  - Only `demangle_simple()` (the generic Itanium-ABI length-prefix
    algorithm) is shared between the two parsers — this is a tool-
    independent C++ ABI fact, not disassembler-specific parsing logic.
- `scripts/run_cross_tool_validation.py` — runs the artifact's *matching*
  toolkit's `nvdisasm` (CUDA 12.8 cubin → CUDA 12.8 `nvdisasm`, CUDA 13.3 →
  CUDA 13.3), records the exact command/return code/stderr/version/raw
  JSON path for every artifact, classifies with the same shared policy
  function used for cuobjdump (`classify_binary.classify_kernel` — the
  category *definitions* are the study's codebook and are deliberately
  identical across both paths so a comparison is meaningful; only feature
  *extraction* differs), and compares against the existing
  `results/features.jsonl`.
- `tests/test_nvdisasm_parser.py` — 11 tests against **real** JSON fixtures
  generated by actually running `nvdisasm -c -json` on 4 real corpus
  cubins (`tests/fixtures_nvdisasm/`, both CUDA 12.8 and CUDA 13.3),
  including independently re-deriving the exact O0 indirect-zero-store
  finding from Phase 4 (5 indirect, 0 direct) via this completely
  different JSON-based parsing path.
